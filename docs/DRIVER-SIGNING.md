# Driver signing

Status: **no signing is configured or performed.** CI produces an unsigned
development build. No certificate, private key, or signing identity is present
in this repository.

Signing is not a formality. On Windows 11 x64, an unsigned kernel driver does
not load in normal mode. A self-signed catalog is not a production signature.
This document states the options and the project's policy without overstating
what exists.

---

## 1. What the build produces today

| Artifact | Signature state |
| --- | --- |
| `STGRExt4.sys` | Unsigned |
| `STGRExt4.cat` | Generated by Inf2Cat, unsigned |
| Package ZIP / artifact | Unsigned |
| SHA-256 checksums | Integrity only, not authenticity |

`Invoke-Inf2Cat.ps1` validates the INF and produces a catalog. A catalog is a
list of file hashes; generating one does not sign it. The CI workflow does not
call `signtool`.

`Stage-DriverPackage.ps1` writes `README-UNSIGNED.txt` so a user cannot mistake
the package for a production release.

---

## 2. Windows driver signing requirements

Windows enforces kernel-mode code signing. The exact policy depends on the
Windows version, Secure Boot state, and the driver's load path. In general:

- a production kernel driver must be signed by a certificate chain that the
  target system trusts;
- the driver package catalog must be signed for installation;
- the driver binary itself is also signed;
- Secure Boot adds requirements and can reject otherwise valid development
  signatures;
- test signing is a development mode, not a distribution mechanism.

Do not rely on a blog post or an old tool to "disable" signature enforcement on
a production machine. The supported paths are test signing in a disposable VM
or a properly signed release.

## 3. Options

| Mode | What it is | Suitable for | Limitations |
| --- | --- | --- | --- |
| Unsigned | No signature | Source review, static analysis | Will not load on a normal Windows 11 x64 system |
| Test-signed | Self-signed certificate, `bcdedit /set testsigning on` | Disposable VM development | Watermark, Secure Boot conflict, not for users |
| Attestation signing | Microsoft Partner Center attestation with an EV certificate | Distribution without full WHQL, for many driver types | Requires a verified legal entity and an EV certificate; Microsoft signs the submission |
| WHQL / HLK | Full logo and Hardware Lab Kit testing | Broad distribution, some device classes | Expensive, slow, requires hardware/test evidence |
| Trusted Signing | Microsoft Azure Trusted Signing service | CI signing with a managed identity | Requires onboarding, identity validation, and policy; not configured here |

The project has not chosen a production path. That decision requires a legal
identity, a certificate, and a release process. It is a Milestone 9 item.

### Facts that must not be overstated

- A self-signed certificate is not trusted by anyone else's machine.
- Signing the catalog does not make the driver's code correct.
- An unsigned catalog is a structural artifact, not an installable signature.
- Test signing requires weakening the platform's security configuration.
- A timestamp proves when a signature was made; it does not prove the code is
  safe.
- A SHA-256 file hash proves integrity against the published hash; it does not
  prove who built the file.

## 4. Test signing (development only)

The full procedure is in [`DRIVER-INSTALLATION.md`](DRIVER-INSTALLATION.md).
Summary:

1. Use a disposable VM.
2. Disable Secure Boot in the VM firmware.
3. `bcdedit /set testsigning on`; reboot.
4. Create a self-signed code-signing certificate.
5. Trust it in `LocalMachine\Root` and `LocalMachine\TrustedPublisher`.
6. Sign `STGRExt4.sys`.
7. Regenerate the catalog after signing the `.sys`.
8. Sign `STGRExt4.cat`.
9. Verify with `signtool verify /kp` and install.

The private key stays in the VM. It is never committed, uploaded, or reused.

## 5. Production signing (future)

A future release process must:

1. Build from a tagged commit in a protected CI environment.
2. Produce reproducible inputs and record the toolchain versions.
3. Submit the package for attestation or WHQL as appropriate.
4. Sign with a hardware-backed or managed key; the key never enters the
   repository or a build log.
5. Timestamp the signature with a trusted timestamp authority.
6. Verify the signature on a clean Windows 11 machine with Secure Boot enabled.
7. Publish the signed package, the SHA-256 sums, and the verification command.
8. Keep an audit trail of what was signed and by which identity.

None of these steps exist. The release workflow intentionally creates an
**unsigned pre-release** and says so in its notes.

---

## 6. CI policy

- No signing keys, certificates, `.pfx`, `.pvk`, or `.snk` files are stored in
  the repository.
- No workflow secret is required to build the current artifacts.
- The driver workflow does not sign. It generates an unsigned catalog to prove
  the INF is structurally valid.
- Any future signing job must use a protected GitHub environment with required
  reviewers, short-lived credentials, and no ability to run on pull requests
  from forks.
- A build log must never print a private key, password, or token.

`scripts/Test-Repository.ps1` rejects private key containers and PEM private key
blocks. It is a guard, not a substitute for access control.

## 7. Verification commands

On a machine with the Windows SDK:

```powershell
# Kernel-mode policy for the driver image.
signtool verify /v /kp .\STGRExt4.sys

# Catalog signature.
signtool verify /v /pa /c .\STGRExt4.cat
```

Expected today: failure, because the files are unsigned. That failure is
correct and must not be hidden.

For a future signed release, also verify on a clean machine:

```powershell
Get-AuthenticodeSignature .\STGRExt4.sys | Format-List
Get-AuthenticodeSignature .\STGRExt4.cat | Format-List
```

A valid signature is necessary but not sufficient. The release must still pass
the functional and integrity tests.

---

## 8. Installer requirements (future)

The installer must:

- verify the package signature before copying anything;
- refuse an unsigned package in production mode;
- display the signer identity and the package version;
- check the Windows build and architecture;
- warn that the volume must be approved and backed up;
- provide a clean uninstall that does not touch file system data;
- never enable test signing or disable Secure Boot automatically;
- never install a driver that failed verification.

The current repository has no installer.

---

## 9. Key management rules

1. Never commit a private key.
2. Never paste a key into an issue, chat, or build log.
3. Never share a test certificate between machines.
4. Use a hardware token or managed service for production keys.
5. Revoke a compromised certificate immediately and publish an advisory.
6. Rotate credentials; do not reuse a test identity for production.
7. Store only public certificates and thumbprints in documentation, and only
   when they are meant to be public.
